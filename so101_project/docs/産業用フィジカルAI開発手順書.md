# 産業用フィジカルAI開発手順書　Claude用

[提案書](plan/提案書_産業用フィジカルAIと事業化.md) ｜ [計画書と完了条件](plan/計画書_産業用フィジカルAIと事業化.md)

## 1　最初の作業を開く

[STATUS](../STATUS.md) と担当範囲を確認する。初回の依頼は「架空の排除セルで、似た部品A・Bのうち不良候補Aだけを取り出す。正常・異常を再生し、どの観測で完了か保留を選んだか示す」。まずは生成した画像と模擬信号で判断の部分を完成させる。

プロジェクト直下から既存モデルの対応と検査済みの入力例を確認する。

~~~powershell
Push-Location sim
try {
    node tools/check-urdf.js
    node tools/check-fk.js
} finally { Pop-Location }
~~~

画像制御と物理の既存入口は [パズルの手順書](SO101パズル開発手順書.md) の手順1。以下の架空セルの実行入口は新規実装する。既存チェックの合格と架空セルの検証結果は個別に保存する。

## 2　入力と正解を作る

1. 台・搬送方向・観測区域・排除先・二部品の初期位置を図にする。長さ、角度、時刻の単位と座標の原点を記す。検査判定の発行時に追跡番号を付ける。
2. 制御用の記録を「時刻、画像参照、検査イベント番号、追跡番号、良否候補、設備信号」とする。画像で識別できない個体に描画内部のIDを渡さない。採点側には物体の本当のID、良否、最終位置、操作時刻を別に保存する。
3. 乱数種、初期状態、外乱を固定する。状態は「観測待ち→候補照合→排除指令→再撮影→完了／理由付き保留」。同じイベントの再送では指令を増やさない。タイムアウトと再撮影の上限は各ケースの設定として記録する。

## 3　合否を先に決めて試作する

| 入れる出来事 | 制御と独立採点で確認すること |
|---|---|
| 正常にAを取り出す | 対象が排除先にありBは流路に残る。時刻の合う確認画像を根拠に完了が一度だけ出る |
| 照合前にA・Bの順を入れ替える | 観測で再同定できれば対象だけを取り出す。対応が曖昧なら保留。Bを取り出した場合は採点で誤排除にする |
| 空振りで腕の完了信号だけ返る | 元位置にAが残る。完了に進まず再観測または保留になる |
| 確認画像が欠ける／古い画像が届く | 観測時刻を確認し、期限切れで理由付き保留になる |
| 同じ検査判定が二度届く | 排除指令は一度。二回目のイベントに同じ処理結果を対応付けられる |

同じ観測列のまま、採点側のA・Bだけを逆にして再生する。指令が同一で、誤排除の採点だけが変われば、真値の混入を検出する検算になる。正常でも全件保留にする実装は正常例で落とす。基準方式と候補方式を各ケースで比較し、制御判断、実際の排除先、判定理由を一行ずつ出す。失敗例は直す前の記録を残し、修正後に同じ入力を再生する。

## 4　物理と二社の機種で試す

- まず一手の指令をMuJoCoの自由剛体に適用し、解放後に物体が落ち着いた時刻の画像を返す。採点は最終位置と入った区域で決める。手順3を再生し、接触・滑りで新たに起きた失敗を追加する。[物理の実行例](../sim/physics/README.md)
- 次にワークを固定し、共通工程から機種別に工具先端目標と入出力を変換する。差分表の列は「機種・制御装置、工具と基準座標、単位、教示点、信号、停止復帰、出力形式、試した環境、証拠、未確認」。CRX-20iA/L は既存の教示点を使う撮影工程から、デンソーは選定済みの機種でトレー選別から確認し、共通比較には両者で同じ工程を一件使う。
- 座標変換の往復、到達不能な点、完了信号欠落、未対応命令を試す。両社それぞれで型式と制御装置を記録し、対応するオフライン環境へ下書きを読み込み、座標系と排除・再確認の信号順を照合する。メーカーの環境で確認できた項目に環境・版・結果を付ける。設備受入は現場担当と別途実施し、到達、信号、停止復帰を一項目ずつ記録する。

## 5　納品し、次の案件で再利用する

1. 正常と取り違えの動画を同じ時刻軸で作る。観測画像、選んだ動作、保留理由を重ねる。判断履歴にはケース番号・入力版・実行方法・出力場所を残す。
2. 機種差分表と営業提案見本を添える。提案見本は「顧客の判断したいこと／支給資料／成立範囲／未確認の光学・設備条件／現地試験／見積前提」を一枚にする。4点を架空案件の見本と明記する。
3. 現物案件では品質担当が確認した良品・不良品を用意し、見逃し・誤排除・保留・時間の許容値、実機での試行数、受入判定者を初回見積前に顧客と決める。初回から共通作業と案件固有作業の工数を記録する。二件目は共通部分、案件固有修正、人の監修時間、現場作業、直接原価を一件目と並べて記録する。
4. 各回は「仮説、再現方法、結果、判断、次の一件」を残す。夜間は [夜の開発記録](records/夜の開発_LOG.md) を利用し、担当と次の作業が変わったらSTATUSを更新する。文書更新後はルートで次を実行する。
