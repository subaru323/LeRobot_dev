# core のルール

`方針.md` を、具体的な手順にしたもの。プロジェクトのルールは `docs/rules/` に足す。

## R-001 結論を利用者に出す前に、新しい会話の AI に点検させる

- 根拠: 利用者の判断。core を作った検証で何度も使い、毎回、書いた本人が見落とした問題（事実の誤り、言い過ぎ、測り方の穴）を拾った（`根拠.md`）。ただし、比べる相手（同じ会話での見直し）とは比べていない。先行研究では、新しい会話の点検と、同じ会話での1回の見直しに、はっきりした差は見えていない。
- 使う場面: 実験・調査・分析の結論や、方向を決める提案を、利用者に出す前。実験や大きな作業の計画書を、回す前。
- 点検の手段: 既定は下の `r001_check.py`（新しい会話の AI、自動メモリと CLAUDE.md なし）。**プロジェクトに同じ役の仕組み（並列のサブエージェントの採点役や反証役など）がすでにあれば、それを使ってよい。** ただし、使う場面（利用者に結論や方向の提案を出す前）と、台帳への記録は守る。代えたときに守れないもの（点検役に自動メモリが入る、道具の制限が無い、書き手が依頼文を書くので書き手の見方が混ざりうる）は、台帳の点検ごとの行に書く。どちらが見落としを多く拾うかは確かめていない。入れるときに同じ対象を両方で回して比べるなら、比べる前に数え方（重なった件数、片方だけが拾った件、そのうち事実の誤りだった件）と、点検役の条件（メモリと道具の有無）を決めておく。1回では、どちらが多いかは見分けられない。
- 使わない場面: 進み具合の連絡、ファイルを直したという報告、単純な質問への答え。`方針.md` 1 の「あたりで足りる」場面（その場合は報告に「あたり（状況証拠）」と書く）。
- やり方:
  1. 結論の文書を書き、機械検査をかける（`python docs/core/tools/doc_lint.py <文書>`）。
  2. 点検させる: `python docs/core/tools/r001_check.py <結論の文書> <依頼の要旨> <計画> <出力> [--extra <追加の頼み>] [--allow-read] [--allow-web]`。新しい会話の AI（自動メモリと CLAUDE.md なし、書き込み・シェル・サブエージェントは禁止）が、問題を重い順に最大8件挙げる。`--allow-read` を付けるとプロジェクトのファイルを読めるので、STATUS.md なども読みうる（点検役は出力の最初に、文脈に入っていたものを書く）。依頼の要旨・計画・追加の頼みは短い文書にして渡す。計画が無ければ「計画は無い」と書く。
  3. 挙がった件を1件ずつ、直す・直さない（理由）を、結論の文書の末尾の表に書く。**点検役が挙げた数字や事実は、受け入れる前に自分で確かめる。**
  4. 台帳（既定は `docs/records/R001_LOG.md`）に1件1行で残す: 種類（事実 / 判断）、事実を確かめたか、対応（受け入れ / 一部 / 見送りと理由）、後で誤りと分かったか。
- 費用: 1回 0.5〜2 ドル程度（ファイルを読ませると多くなる）。費用の上限を理由に省かない。
- CLAUDE.md への書き方: 「実験・調査・分析の結論や、方向を決める提案を利用者に出す前に、新しい会話の AI に結論を渡して問題を最大8件挙げさせ、直してから出す。点検役が挙げた数字や事実は、受け入れる前に自分で確かめる。呼び出しは `python docs/core/tools/r001_check.py`。挙がった件は `docs/records/R001_LOG.md` に記録する。」

## 試行中の手順

確かめきれていないが、使ってよい手順。使ったら、役に立ったか・邪魔だったかを記録する。

- 計画書の書き方: `guides/計画書の書き方.md`
- 短く通す6つの問い: `guides/簡易版の問い.md`
