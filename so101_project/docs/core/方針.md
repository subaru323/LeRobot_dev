# core の方針

このプロジェクトのルールの土台。`docs/` の core 以外のフォルダに、プロジェクトが自分でルールを足していく。**足したルールは、この方針に反しないこと。** 反したほうがよいと思ったら、プロジェクトのルールで方針を曲げず、`docs/core_proposals/` に修正案を書く（`修正案の出し方.md`）。

各項目の「根拠」は、core を作るときに見た材料の強さ。**確かめた**（実験や実物で見た。範囲つき）/ **利用者の判断**（利用者が決めた）/ **先行研究**（論文の報告）/ **ほかのプロジェクトの実績**（そのプロジェクトで続けて使われ、失敗の記録から作られたもの。core では比べて確かめていない）/ **試行中**（使いながら確かめる）。詳しくは `根拠.md`。

## 1. 正しさを優先する。ただし完ぺきは目指さない

| 場面 | どこまで確かめるか |
|---|---|
| **あたりで足りる**: 次に何を調べるかを決める、元に戻しやすい判断、出力や記録で直接確かめた事実の報告 | 状況証拠でよい。費用を抑える。報告に「あたり（状況証拠）」と書く |
| **確かめる**: ルールにする、方向を大きく変える、利用者に手間を頼む、元に戻しにくい（機器を壊しうる、データを消す、外に出す） | 確かめる。結論は R-001 の点検を通す。費用を理由に点検を省かない |
| 迷ったとき | 間違えたときの手戻り（時間・費用・機器）が、確かめる費用より大きければ確かめる |

根拠: 利用者の判断。

## 2. 実物で確かめる。読んで考えるだけで済ませない

- 前提（仕様、寸法、通信、性能、ライブラリの挙動、データの中身）は、**実物を動かすか、一次資料で確かめてから**計画や結論に使う。確かめていない前提は「未確認」と書く。
- 誤りや弱点を探すとき、同じ AI が手がかり無しで見直すより、**外からの手がかり**（テストの結果、実機の測定、ログ、起きた事実）を渡すほうが直る。
- 根拠: 前提を実物で確かめることは、利用者の判断。外からの手がかりは、先行研究（手がかり無しの自己修正は良くならないか悪くなる、外の検証器の結果を返すと良くなる、という報告が多い）と、試行中（core を作った検証では、起きた失敗そのものを渡すと直った。2ケースだけの探索）。

## 3. 結論は、別の目で点検してから出す

- 実験・調査・分析の結論や、方向を決める提案を利用者に出す前に、新しい会話の AI に点検させる（`rules/RULES.md` の R-001）。プロジェクトに同じ役の仕組み（並列のサブエージェントの採点役・反証役など）がすでにあれば、それで代えてよい。代えたときは、点検役に自動メモリが入っていたか、道具が使えたか、書き手が依頼文を書いたか（書き手の見方が混ざりうる）を台帳に書く。
- 点検役が挙げた数字や事実は、受け入れる前に自分で確かめる。挙がった件は台帳に残す。
- 根拠: 利用者の判断（点検は何度も見落としを拾ったが、「新しい会話で」やる意味は、まだ確かめられていない）。

## 4. 書き方

- **言える範囲で書く。** 差が見分けられない結果を「効かない」「差は無い」と書かない（「この規模では見分けられない」）。後から眺めて作った説明は「仮説」と書く。
- **数字は出力から写す。** 結論の数字は、集計の道具の出力や記録から取る。手で計算した数字を結論に書かない。
- **いまの結論を冒頭に置く。** 結果や調べものの文書は、冒頭に「いまの結論」を置き、変わったら書き換える。撤回した文は、本文の場所で打ち消し線を引く（後ろに追記するだけにしない）。
- **根拠の強さを書く。** ルールごとに、確かめた / 利用者の判断 / 先行研究 / ほかのプロジェクトの実績 / 試行中 を書く。報告や結論の確からしさには、確かめた / あたり（状況証拠）を書く。
- 根拠: 数字を出力から写すことは、確かめた（手で書いた数字の結論に誤りが出た）。言える範囲で書くことは、確かめた（「効かなかった」と書いた結論を、後で撤回した）。いまの結論を冒頭に置くこと・撤回を本文で打ち消すことは、試行中（引き継いだ AI が、後ろに追記するだけの文書を「追いにくい」「見出しだけ読むと誤る」と挙げた。置いた後に誤読が減ったかは確かめていない）。根拠の強さを書くことは、利用者の判断。どれも1つのプロジェクトでの観察。

## 5. 利用者とのやり取り

- 長い作業の前に、最終目標と、何が分かったら終わりかを聞く。**ただし、答えを待つ間も、確認なしで進められる部分は進める。** 進めてよいのは、元に戻しやすい部分（方針1 の「あたりで足りる」場面）。
- 利用者に手間を頼む前に、手間と今できるかを聞く。まず自分で調べる。
- 造語を使わず、噛み砕いて書く。決めてほしいことを先頭に書く。
- 提案は、2つ以上の案と推奨、「何が分かったら推奨を変えるか」を付けて出す。
- 根拠: 利用者の判断。

## 6. 入口と記録

- 入口は `CLAUDE.md`（自動で読まれる）→ **入口の文書**。入口の文書には、最終目標、優先順位、採用ルール、現在地、次の一手、利用者の判断待ち、読む順を書く（置き場所を分けてもよいが、入口の文書から指す）。core の雛形では `STATUS.md` と呼ぶ。**プロジェクトに同じ役の文書がすでにあれば、それを入口の文書とみなしてよい**（名前はプロジェクトが決め、CLAUDE.md から指す）。
- **書くのは逐一。** 次の一手、決まったこと、分かったことが変わったら、その場で入口の文書を直す。会話の終わりにまとめて書くことにしない（会話がいつ切れるか分からない）。少なくとも会話の終わりには、変わったことが書けているかを確かめる。**日付だけを書き換えない**（変わったことが無ければ書かない。日付だけ新しいと、古さの確認が効かなくなる）。
- **複数の会話で動かすときは**、次の一手を会話ごとの欄に分ける。進行は方針11 の会話ごとの記録に書き、入口の文書にはその置き場所だけを書く。
- 入口の文書には**状態の数字（合否・件数・進行・結果）を写さない**。数字は、道具の出力か正本（結果の文書、集計の出力）へのリンクにする。次の一手の費用や時間の見込みは書いてよい。
- 事実ごとの持ち主と、食い違ったときの順位は、方針12。
- 新しい会話の最初に、入口の文書が古くなっていないか（最終更新の日時と、実際の状態）を、できれば道具で確かめる。
- 根拠: 入口を CLAUDE.md から指すことは、試行中。core を作った検証で、短い CLAUDE.md（STATUS.md を読む・更新する、と R-001 の1段落）を置いた形では、小さい作業でも STATUS.md が読まれ、更新された。置かない形では読まれなかった（各2回、1つのプロジェクト、1つのモデル）。結論を出す作業では、CLAUDE.md が無くても読まれた。差が「自動で読まれること」と「書いた中身」のどちらによるかは分けていない。core の雛形の CLAUDE.md は、そのときの形に足したもので、この形のままでは試していない。逐一書くこと、入口の古さの確認、日付だけを書き換えないことは、ほかのプロジェクトの実績（core では比べていない）。

## 7. 道具で守る

- 機械で検査できる決まりは、道具で検査する（`tools/doc_lint.py`、`tools/r001_check.py`）。覚えて守るだけにしない。
- **決まりを作ったら、同じ回に「機械でどう確かめるか」と「いつ回すか」を決め、一覧にする**（決まり ⇄ 検査 ⇄ 回す時機）。機械で見られない決まりは、なぜ見られないかを書く（空欄にしない）。**回していない検査は、無いのと同じ。**
- 根拠: 確かめた（決まりを書いた本人が、長い作業の中で同じ決まりを破った。検査の道具は、過去の文書の違反を拾えた。ただし空振りも多い）。一覧と時機は、ほかのプロジェクトの実績。ただし材料は「一覧を作る前は、検査の道具の多くが長く回されていなかった」という失敗の記録までで、一覧を作った後に回るようになったかは core では見ていない。

## 8. 作業の範囲

- 作業フォルダの外を探さない。手元に無い資料（正解、過去の記録、ほかのプロジェクトのファイル）は、探しに行かず、利用者に置き場所を聞く。
- 実験や点検の AI を道具で起動するときは、利用者の自動メモリを入れない（`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`）。読むだけの AI には、書き込みとシェルの道具を禁じる。チャットの中のサブエージェントで代えるときは、これが守れないことを台帳に書く（方針3）。
- 根拠: 外を探さないことは、試行中（試験の AI が、手元に無い正解や過去の記録を作業フォルダの外まで探しに行った）。自動メモリは、確かめた（実験の AI に利用者のメモリの索引が入っていた。結果への影響は見込みの段階）。読むだけの AI に禁止を明示することは、確かめた（「使ってよい道具」を指定するだけでは、ほかの道具が使えた）。

## 9. 費用

- 費用は無駄にしないが、正しさが先（1）。結論の点検（3）は、費用の上限を理由に省かない。
- 見積もりは、トークンではなく、ドルか時間で書く。
- 根拠: 利用者の判断。

## 10. ファイルを書き換えるとき

- **元を消さない書き方をする。** 正本はバックアップを取ってから直す。書き込みは、先に文字の変換を済ませ、一時ファイルに書いてから差し替え、直後に大きさを確かめる（開いた瞬間にファイルが空になる書き方で、途中で落ちると空のまま残る）。
- **書き換えのスクリプトは、ファイルに書いてから実行する。** シェルのヒアドキュメントや、記号を特別に扱う文字列（PowerShell の二重引用符など）に通さない。記号や改行が化けて、静かに壊れる。
- 書いたファイルは、制御文字が混ざっていないかを検索する（構文の確認では見つからないことがある）。
- 一括で書き換える道具は、中身が変わらないファイルを書かない（改行の形などが変わる）。
- 根拠: 確かめた（core を作った検証で、PowerShell の文字列で記号が消え、文書が壊れた。一括の道具が、中身の変わらないファイルの改行の形を変えた）。ほかのプロジェクトの実績（大事な文書を0バイトにした。同じ晩に、ファイルに書いてから実行した10回以上は0回化け、ヒアドキュメント経由は4回化けた）。

## 11. 複数の会話で動かすとき

- **担当はファイル単位で分ける。** 危ないのは、同じ既存ファイルを2つの会話が書くこと。新しいファイルは、どこに作ってもぶつからない。
- 複数の場所で使う共有の部品は、正本を1つ決め、正本だけを直し、配ったら一致を確かめる。
- **生成物（キャッシュ、台帳、集計の結果）を書き換える作業は、1つの会話に寄せる。** 2つの会話が書くと、どちらの結果か言えなくなる。
- **進行は、1つの文書に複数の会話で追記しない。** 会話ごとの記録（1行ずつ追記するファイル）に書き、読むときに道具で時刻順に混ぜる。
- 会話どうしの受け渡しは、文章で「こう直して」と書くより、当てるだけの道具やファイルで渡す。
- 生成物を変える変更が重なるときは、順番待ちの列に積み、どれから当てるかは道具に決めさせる（試行中。ほかのプロジェクトの仕組みを、要約で聞いただけ）。
- 根拠: ほかのプロジェクトの実績（同じ文書への同時の追記で行が混ざった。共有の部品を一部にしか直さず割れた。受け渡しを文章でした回は、受け手が手で直して遅れた）。材料は失敗が起きた記録までで、決まりを入れた後に減ったかは core では見ていない。

## 12. 事実の持ち主と、食い違ったときの順位

- **同じ事実を2か所に書かない。** どの文書が何の正本かを一覧にする（docs の置き場所の表）。
- **順位の先頭は、いつも利用者の最新の発言と、記録された利用者の決定（日付の新しい方）。**
- その次は、2本に分けてよい。**どう作業するか**（ふるまいの決まり）: core の方針 → プロジェクトのルール → そのほかの文書。**何を作るか**（仕様・要件・課題・計画）: プロジェクトが決める（例: 絶対条件の文書 → 仕様 → 課題 → 計画）。
- **軸は文書ではなく中身で分ける。** 仕様や計画の文書でも、どう作業するかを書いた部分（「この作業は点検を省く」など）は、ふるまいの軸として core に従う。仕様の軸の順位は、core の方針を外す理由にならない。軸をまたいで食い違ったら、利用者に確かめる。
- 下の文書が上と合わないと分かったら、上を正として下を直す。上が古いと思ったら、利用者に確かめて上を直す。**上が core なら直さず、`docs/core_proposals/` に修正案を書く。**
- **例外（状態の記述だけ）**: 上位の文書に残った古い状態の記述のうち、検査の道具が出す合否・件数・進み具合だけは、利用者に確かめずに、その道具の出力（正本）へのリンクに置き換えてよい（数字を書き写さない。方針6）。使う道具は検査の一覧（方針7）に載っているもの。直したことを記録に残し、後で利用者に知らせる。core と、記録された利用者の決定には当てない。**それ以外の上位の文書の書き換えは、利用者が決めたときだけ。**
- 根拠: 持ち主を決めて同じ事実を2か所に書かないこと、1本の順位は、ほかのプロジェクトの実績（core では比べていない）。2本の軸と、状態の記述の例外は、試行中（ほかのプロジェクト（ちくわ排除機構）からの修正案を、歯止めを足して取り込んだ。core の形では試していない。材料はそのプロジェクトの決まりと、1件の例）。
