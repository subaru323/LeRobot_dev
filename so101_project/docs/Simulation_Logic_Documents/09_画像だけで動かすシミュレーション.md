# 09 画像だけで動かすシミュレーション

作った日：2026-11-17。利用者の指示「シミュレーションにはカメラの位置からの画角が必要だし、その画角だけを使ってロボットのプログラムを出力してアームを動かすシミュレーションが必要じゃない？いまのはただ、規定通りに動いてるだけ」（2026-11-17）から作った。

この文書が答える問い：カメラの絵だけから、ロボットのプログラム（関節の列）を出して腕を動かすシミュレーションを、どう組むか。いまの `sim/` と何が違い、何を足せばよいか。

**状態：設計。下見の道具だけある**（2026-11-17、別の会話が `sim/vision.js`・`sim/tools/vision-loop.js` を書いた。上の絵を作り、色と明るさだけからピースを見つけ、正解と比べる。画面にはまだ出ていない）。画面での見せ方とリアルタイムの判断は §6（利用者 2026-11-17）。

## 1. いまの結論（2026-11-17）

- いまの `sim/` は、ピースの**本当の置き場**から動きを決めている。カメラの絵は「写るか」を数えるのに使うだけで、動きを決めるのには使っていない。だから、カメラ・見つける道具・校正の誤差が、どこにも出てこない（[00 の条件 14](00_絶対条件.md#条件-14-動きはカメラの絵だけから決めるこちらで足した)）。
- 組み方：シミュレータを「世界」（本当の置き場を持ち、絵を作り、動きを流して採点する）と「制御プログラム」（絵だけを受け取り、関節の列を返す）の 2 つに分ける。**制御プログラムは、実機で使うものと同じ**（[08 §5](08_カメラ_配置と配線とプログラム.md#5-プログラムの組み方)）。
- いまある部品で、半分は組める：上のカメラの絵を撮る（`index.html?_cam=top`、S-9）、その絵の正解の画素（`overhead-truth.js`）、置き場 JSON を読んで動きを決める（`check-layout.js`）、関節の列を書く（`export-motion.js`）。**無いのは**、絵からピースを見つける道具（K6）、手首のカメラの絵、計画の口、本当の置き場で流して採点する所、乱しを入れて何回も回す所。
- 先に直すこと：腕どうしの当たり（[00 の条件 5](00_絶対条件.md#条件-5-腕の自分との当たりを忘れない)）と、写す姿勢（[08 §2](08_カメラ_配置と配線とプログラム.md#2-いまの置き方は正しいか確かめたこと)）。めり込む姿勢で撮った絵から始めても、実機の練習にならない。

## 2. 組み方

```
┌──────────────── 世界（sim/。本当の置き場を持つ） ────────────────┐
│  本当の置き場 truth.json（制御からは読めない）                     │
│  絵を作る: 腕の姿勢 q と置き場 → 上の絵 / 手首の絵（three.js）      │
│  流して採点: 関節の列を本当の置き場の上で流す                       │
│     → 当たり（腕どうしを含む）・つかめたか・置いたずれ・時間        │
└───────────────▲─────────────────────────────┬────────────────┘
        絵・関節の読み │                              │ 関節の列
┌───────────────┴─────────────────────────────▼────────────────┐
│  制御プログラム（実機と同じもの。見つける道具は JavaScript）       │
│  見つける（絵 → 置き場の見積もり）→ 決める（sim/ の計画の口）      │
│  → 換算 → 送る。手首で確かめて直す                               │
└──────────────────────────────────────────────────────────┘
```

- 制御プログラムが「世界」とやりとりする口は、実機の腕とやりとりする口と同じ形にする：**絵を読む**・**関節の今の角度を読む**・**関節の目標を送る**。シミュレーションでは、その口の後ろが「世界」（仮の名前 `SimRobot`）、実機では SO-101 のバスとカメラ。こうすると、シミュレーションで通った制御プログラムを、書き換えずに実機につなげる。
- 「決める」で使う当たり判定は、制御の側の**見積もった置き場**で通す。「流して採点」の当たり判定は、**本当の置き場**で通す。2 つの差が、見積もりの誤差で起きる当たり（見積もりでは当たらないのに、本当は当たる）。これが、いまの `sim/` では一度も出てこない失敗。
- ロボットのプログラム（出力）は、いまの `export-motion.js` の関節の列（JSON・CSV、30Hz、URDF の角度）を元にする。実機へは、LeRobot の角度に換算してから送る（V-4）。

## 6. 画面での見せ方と、リアルタイムの判断（2026-11-17）

**見つける道具は JavaScript 1 本**（利用者の決定 2026-11-17「JavaScript 1 本」）。画面の中も、node の道具も、実機も、同じ `vision.js` の `detect` を使う。Python・OpenCV の見つける道具は作らない。実機では、Python がカメラの絵を取り（LeRobot の `OpenCVCamera`）、その絵を node の `detect` に渡す口が要る（[08 §5](08_カメラ_配置と配線とプログラム.md#5-プログラムの組み方)）。

利用者の指示「シミュレーションには各カメラの画角も表示するようにしてほしい。そして、その画角をみて、リアルタイムで判断して、行動を選択するってロジックと見せ方にしてほしい」（2026-11-17）。**状態：一部を作った**（`sim/live.html`。§6-6）。1 手ずつ組む口はまだ無く、全部の手をまとめて組み直す形で代えている。

### 6-1. いまとの違い

| | いまの画面（`index.html`） | 作るもの |
|---|---|---|
| 動きの決め方 | 開いたときに、本当の置き場から全部の手を前もって決め、それを流す（再生） | 1 手ずつ、**いまの絵を撮る → 見つける → 次の 1 手を選ぶ → 動く → また撮る** を繰り返す |
| カメラ | 「上のカメラから」「手首のカメラから」の視点はある（`scene-data.js` の視点の一覧・`index.html` の `view`・`track`）。画角の四角錐と、カメラの絵の窓は無い。`vision.js` は読み込まれているが、画面からは使われていない | 3D の中に各カメラの画角を出し、各カメラの絵を画面の隅に常に出す |
| 判断の見え方 | 無い（表に結果だけ） | 絵の上に「何を見つけたか」、横に「何を選んだか・なぜか」を出す |

### 6-2. 見せ方

1. **3D の中の画角**：上のカメラと手首のカメラから、見える範囲の四角錐を線で描き、机の上で絵に入る範囲（足跡）を薄く塗る。手首のカメラの四角錐は腕と一緒に動く。カメラごとに色を分け、画角（縦・横の度）と画素数を添える。**画角の値には【仮】を付ける**（上のカメラは「画角は分からない（品の資料で確かめる）」、手首のカメラは `scene-data.js` に 60°【仮】があるだけ）。**画角は `so101.js` の 1 か所に置き、四角錐・窓・見つける段・世界の絵の全部がそこを読む**（いまは 60・70 があちこちに直接書かれている）。
2. **カメラの絵の窓**：画面の隅に「上のカメラ」「手首のカメラ」の 2 つの窓を置き、そのカメラの絵を出す。**窓に出すのは `vision.js` の `render` の絵**（見つける段のしきい値と「いちばん明るい面 = 上の面」は、この絵の光に合わせてある。three.js の絵は使わない）。窓の絵は、判断が受け取る絵と同じものにする。縦横は 640×480 のまま（3D の視点のように窓の形に合わせない）。
3. **絵の上の重ね書き**：見つけたピースの輪郭・真ん中・向きを、窓の絵の上に重ねる。見つからなかったピースも分かるように出す。
4. **判断の欄**：いまの段（撮る・見つける・選ぶ・動く）を光らせ、**実際に選んでいるものだけ**を出す：見積もった位置と向き、爪の向き（`yp` か `yp`+180°）、回す向き、運ぶ高さを上げる 4 通りのどれか、腕どうしの隙間。取るピースの順番は、いまは盤の上の解き方だけで決まる（`puzzle.js`）ので、「選んだ」とは書かない。
5. **本当と見積もりの差**：切り替えで、本当の置き場（世界の側）を薄く重ね、見積もりとの差（mm・度）を出す。**判断には使わない**、見る人のためだけの表示であることを画面に書く。
6. **途中でかき乱すボタン**：まだ取っていないピースを少し動かす・回す。次に撮った絵でそれに気づいて、動きが変わるところを見せる。これが「前もって決めた動きの再生ではない」ことの、目で見える証拠になる。いま運んでいるピースは対象から外す。

### 6-3. 判断のしかた（1 手ごとのループ）

```
写す姿勢で撮る（世界が、写す姿勢と本当の置き場から上の絵を作る）
 → 見つける（制御が、絵だけから置き場を見積もる。vision.js の detect）
 → 選ぶ（制御が、いまの関節・置き済みのピース・見積もった置き場から、次の 1 手を組み、当たり判定を通す）
 → 動く（世界が、その 1 手を本当の置き場の上で流し、当たり・つかめたかを採点する）
 → 写す姿勢へ戻る → 最初に戻る
```

- **上のカメラで撮るのは、写す姿勢のときだけ。** 隠れる点を数えたのは写す姿勢だけ（[00 の条件 6](00_絶対条件.md)）で、`detect` は、爪に持ったピースや腕が写ると見積もりが狂う。写す姿勢との行き来は手ごとに増えるので、**その行き来も、腕どうしの判定に通す**（前の写す姿勢では、めり込みがこの区間で出た。[00 の条件 5](00_絶対条件.md#条件-5-腕の自分との当たりを忘れない)）。
- **手首のカメラ**は、窓に絵を出すところまでを先に作る。手首の絵で合わせる段（§4 の I-5）は後の段：いまの `detect` は、どれか 1 個でも 20 画素に足りないと失敗にするので、1 個しか写らない手首の絵には使えない。狙うピースを 1 個だけ見つける口を新しく作る。
- **新しく作る口が要る**：いまの `buildFromUi` は、写す姿勢から全部の手を決め、全部のコマを組んでから当たりをまとめて見る。「始まりの状態（関節・置き済みのピース・見積もった置き場）→ 次の 1 手と判定」を返す口は無い。
- **時間**（node で測った値。ブラウザの値は §6-6）：全部の手を決めるのに 25.8〜55.4 秒（種 0〜3、点検 C20 の点検役）。割り算での目安は 1 手 9〜11 秒（1 手だけ組む口が無いので、測っていない）。絵を作る `render` は 1 枚 0.3〜0.5 秒、`worldTris` 0.65 秒、`detect` 0.05〜0.09 秒で、重いのは選ぶ段。ブラウザでは計算と描画が同じ流れなので、**計算を小分けにして画面に処理を返し**、「考え中」の表示と 3D が止まらないようにする。速くするために判定を粗くするなら、[00 の条件 13](00_絶対条件.md)（答えが変わらないことを機械で示す）を守る。

### 6-4. 世界と制御を、画面の中で分ける

- §3 の守ることは、そのまま守る。いまは `index.html` が全部のスクリプトを同じ場所で読み、`SCENE_DATA`（開いたときに本当の置き場から作られる）も誰からでも見える。なので、次のように分ける。
  - **世界の絵だけを作る口**を新しく作る。いまの `worldTris` は `buildFromUi` の戻り値を要るので、絵を作るだけで本当の置き場で計画が流れてしまう。
  - **制御は、絵と関節の読みと置き済みの記録だけを引数で受け取る、閉じた部品にする**。本当の置き場の変数に届かない。
  - 本当の置き場は `?LAYOUT=` で、既定（`placeSlots`）と違うものを渡す。
- **制御が信じるカメラは、世界のカメラから【仮】の幅でずらした別の値にする**（`vision-loop.js` の `perturbCam` と同じ考え）。絵から校正する段（机の印・チェッカーボードを世界の絵に描く）は後の段で、それまでは §3 の 2 行目を満たしていないことを、画面にも書く。

### 6-5. できたと言うための確かめ

| 確かめ | 期待 |
|---|---|
| 窓の絵と判断の入力が同じ | 同じコマで、`detect` に入る直前の画素の要約値と、窓の画素の要約値が同じ。負の検算：窓の側だけ雑音の種を変えると合わなくなる |
| 制御が本当の置き場を読まない | §3 の道具に加えて、絵を外から差し込める口を作り、絵を同じにしたまま本当の置き場だけを変える → 選ぶ手が 1 文字も変わらない |
| かき乱しに追いつく | 雑音の種を固定し、まだ取っていないピースを 20mm【仮】動かす → そのピースの見積もりが、動かした向きに 20mm ± 許せる幅だけ動き、ほかのピースは許せる幅より動かない。そのうえで、選ぶ手か動きが変わる |
| 画角が合っている | three.js の `PerspectiveCamera` で机の点を写した位置と、`vision.js` の式で写した位置が合う（`check-overhead-truth.js` と同じやり方）。負の検算：縦の画角を 55° に取り違えると合わなくなる。手首も同じ |
| 採点 | 4 種と置き場の例で、つかめたか・当たり（腕どうしと、写す姿勢との行き来を含む）・置いたずれを、本当の置き場で出す。見積もりの誤差で起きた失敗は、失敗として数える |

- いまの見つける誤差は小さい（報告では 3×4 で 0.09mm）。だから、かき乱しが無ければ、出てくる手は本当の置き場から決めた手とほぼ同じになる。違いが見えるのは、かき乱し・カメラのずれ・雑音を入れたとき。

### 6-6. いまの画面（`sim/live.html`。2026-11-17）
