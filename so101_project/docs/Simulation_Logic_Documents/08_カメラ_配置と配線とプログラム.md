## 4. ケーブルのつなぎ方

**状態：設計。** カメラの品が決まっていないので、ケーブルの長さ・端子の形は決まっていない。

### つなぐ物（パソコンの USB の口）

| つなぐ物 | 何の線か | 口 | 出どころ |
|---|---|---|---|
| フォロワーの基板 | モーターの線（COM11） | USB | [組み立て手順書](../組み立て手順書.md) STEP 2 の表 |
| 上のカメラ | USB（映像と電源） | **パソコン本体の、ほかのカメラと別の口** | [03 撮影台とカメラ](../目的別/03_撮影台とカメラ.md) の 3（同じハブに 2 台だと帯域が足りなくなりやすい） |
| 手首のカメラ | USB（映像と電源） | 同上 | 同上 |
| （リーダー） | モーターの線（COM10） | USB | パズルでは使わない（案 A はリーダー不要） |

- 2 台が同時に 30 fps で撮れるかは `python tools\camera_check.py <上の番号> <手首の番号>` で確かめる。足りなければ `--fourcc MJPG`（[03](../目的別/03_撮影台とカメラ.md) の 4）。
- **カメラの番号は、差し直すと変わることがある**（Windows はカメラを番号で開く。`OpenCVCameraConfig` の `index_or_path`）。使う日の始めに `lerobot-find-cameras opencv` の写真で、どちらが上か手首かを確かめる。番号の表の置き場は、カメラが届いたら [組み立て手順書](../組み立て手順書.md) STEP 2 の表の隣に作る（決まっていない）。

### 上のカメラのケーブル

- カメラ（台の上の部品）→ **柱の、腕と反対の側**に沿って下ろす → 板の外へ出す → パソコン。
- 柱は腕の届く範囲の中にある（§2 の #3）。だからケーブルを柱の腕の側に回さない。結束バンドで柱に留める。
- `sim/` では、ケーブルを留めた柱を、ケーブルの太さだけ太らせて当たり判定に入れる（[K-07](現在の課題.md#k-07)）。

### 手首のカメラのケーブル（いちばん気を付ける所）

- カメラ（手首の台）→ 爪の付け根 → 手首 → 前腕 → 上腕 → 土台 → パソコン。モーターの線と同じ道に沿わせて留める。
- **関節ごとに、曲がる分のたるみを残す**（手首の回転・手首の曲げ・肘・肩の上げ・肩の回転）。たるみが足りないと、腕を伸ばしたときに引っ張られ、カメラの台やコネクタが抜ける。
- **手首の回転（j5）は、ケーブルを巻く。** ちくわでも「手首の巻き（ケーブル）」を課題にした（ちくわの K-90）。動きを決めるときに、手首の回転を決めた範囲の中に収め、行って戻る向きを揃える（巻きっぱなしにしない）。範囲は決まっていない（[K-08](現在の課題.md#k-08)）。
- ケーブルの重さと硬さは、腕を引く。腕の誤差（K1）は、**ケーブルを付けた状態で測る**。
- `sim/` では、ケーブルは形が無い。まずは腕の部品に沿った太さの管として当たり判定に入れ、たるみの輪は「爪・ピースに近づけない範囲」として入れる（[K-07](現在の課題.md#k-07)）。

## 5. プログラムの組み方

**状態：設計。どのプログラムもまだ書いていない（下の「ある」と書いた物を除く）。**

### 形：1 本の制御プログラム + `sim/` を計画と判定に使う

```
[カメラ] ──絵──▶ (1) 撮る ──▶ (2) 見つける ──置き場 JSON──▶ (3) 決める（sim/）──関節の列──▶ (4) 換算 ──▶ (5) 動かす ──▶ [腕]
   ▲                                                    当たり判定を通す                                    │
   └────────────── (6) 手首で確かめる・(7) 上で確かめる ◀──────────────────────────────────────────────┘
```

| 段 | すること | 何で | ある / 無い |
|---|---|---|---|
| (1) 撮る | 上と手首の絵を取る | LeRobot の `OpenCVCamera`（`lerobot.cameras.opencv`。`index_or_path`・幅・高さ・fps・`fourcc`） | 部品はある（`tools/camera_check.py` が同じクラスを使う） |
| (2) 見つける | 絵 → ピースの位置と向き（机の上の mm と度）。色で切り出し、上の面の高さ（14mm）で画素から机へ戻す | **JavaScript（`sim/vision.js` の `detect`。node で動かす）**（利用者の決定 2026-11-17「JavaScript 1 本」。Python・OpenCV では作らない）。Python は絵を node に渡す。カメラの中の校正（チェッカーボード）と、机の四隅の印で出した姿勢を使う | 下見の道具がある（`vision.js`。three.js の絵でだけ試した）。絵を node に渡す口・実物の絵での試し（K6）・校正（K5）は無い |
| (3) 決める | 置き場 JSON → 解き方・動き・当たり判定 → 関節の列（URDF の角度・30Hz） | `sim/`（node）。置き場 JSON は `sim/layouts/*.json` と同じ形 | 半分ある（置き場を読む `check-layout.js`、列を書く `export-motion.js`）。1 本のコマンドにまとめる口が無い |
| (4) 換算 | URDF の角度 → LeRobot の角度（`shoulder_pan` など、度） | Python | 無い（式は K1 で作る。V-4） |
| (5) 動かす | 列を 30Hz で送る | `tools/safe_teleop.py` と同じ作り：`connect_bus_no_torque` → `limit_follower` → `torque_on_in_place` → `sync_write("Goal_Position")` で 1 コマの動きに上限、負荷で止める | 作りはある（[P-001](../rules/RULES.md)）。列を送るプログラムは無い |
| (6) 手首で確かめる | つかむ場所の上で止まり、手首の絵でずれを測る → 直す動きを (3) で判定してから動く | Python（絵を取る）+ `sim/`（ずれを測る・判定。JavaScript） | 無い（K7。決めたこと 6） |
| (7) 上で確かめる | 終わりに上で写し、置いたずれを測って記録 | Python。記録は `tools/eval_log.py` | 記録の道具はある |

- **(3) を `sim/` にやらせる理由**：当たり判定の持ち主を 1 つにするため（ちくわの「絵と判定は同じ値から」）。Python に同じ判定を書き直すと、2 つがずれたときにどちらが正しいか分からなくなる。
- **(5) は本家の `robot.connect()` を使わない。** 目標位置を合わせずに力を入れると腕が跳ぶ（[P-001](../rules/RULES.md)・`tools/so101_common.py` の注）。
- **動きは利用者が作った姿勢から始める**（P-001）。いまの `sim/` の動きは写す姿勢（`PHOTO_Q`）から始まる（`scene-data.js` の `qCur`）ので、(3) の計画の口は「始まりの姿勢」を受け取り、そこから写す姿勢へ行く所も計画して判定する。
- 止める条件（【仮】。ちくわの「異常は止めて人が戻す」）：見つからない・解けない・判定が ng・負荷が高い・手首で測ったずれが許せるずれより大きい → 腕をその場で止め、人を待つ。

### 制御プログラムの骨組み（書いていない。形を示すだけ）

```python
# 名前は仮: tools/puzzle_run.py   （.venv の python で流す。腕は利用者のタブで）

while plan.steps:                  # (5) 1 コマの動きに上限。負荷で止める
    step = plan.steps.pop(0)
    robot.send_joints(urdf_to_lerobot(step.q), step.jaw)      # (4)(5)
    if step.kind == "wrist_check": # (6)
        d = measure_offset(robot.read_camera("wrist"), calib_wrist)
        plan = run_sim_planner(layout_with_offset(layout, d),  # 残りを組み直す。直す動きも (3) で判定してから
```
