# 記録の照合（T0）：LeRobot 0.6.2 の記録を、読込口で照らし合わせる

- 作った日：2026-11-24。利用者の「T0 を始めて」から。段の定義は [総合計画書](../plan/総合計画書_レビュー用.md) §6 の T0。点検 C68（[R001_LOG](../records/R001_LOG.md)）。
- 道具：`tools/t0_record_check.py`（`MAIN_PG/lerobot/.venv` の python で流す）。数字の持ち主は道具の出力（`outputs/t0/`）。

## いまの結論

- **模擬では、ファイルと読込口の照合ができた。** 本家 0.6.2 の読込口（`LeRobotDataset`）で、正面と手首の絵・時刻・関節値・指令・エピソードの境目を照らし合わせる。書いた後でファイルを壊した 3 通り（行を消す・時刻をずらす・境目をずらす）は、毎回 fail で見つかった。
- **信号の警告（warn）は、模擬の 9 エピソードで合わせた【仮】。** カメラの止まり、読み取りの止まり、ループの飛び、列のずれ、カメラの遅れの 5 通りは、9 通り×種 3 つの 27 回とも、入れたエピソードで警告が出た。ずれの無い記録 3 つでは警告 0。ただし、
  - 1 つの種の中では、ずれを入れていないエピソードはどの記録でも同じ中身になる（乱数を同じ順に使うため）。なので、ずれの無い記録として数えられるのは 3 エピソード×種 3 つ＝ **9 エピソード（4 秒ずつ、合わせて 36 秒）** だけ。
  - 模擬の動きは、検査が働くように作り替えた（後の「遅れの見方」）。種 2・3 は乱数を替えただけで、作り方は同じ。
  - 判定はエピソードの単位。警告の出たフレームが、入れた区間とどれだけ重なるかは見ていない（種 2 の `stale_front` は、入れた 18 フレームのうち 10 フレームで警告）。
  - **実物の記録での誤った警告の数は分からない。** 実物ではまだ一度も流していない。
- **本家 0.6.2 の記録の `timestamp` は、測った時刻ではない。** `add_frame` が「フレーム番号 ÷ fps」を書く（`MAIN_PG/lerobot/src/lerobot/datasets/dataset_writer.py` の 224 行）。なので、カメラの遅れ・ループの遅れ・読み取りの止まりは、時刻の列には出ない。道具は信号から探す（画像の変化と関節の動き、指令と状態）。ループが遅いことは、記録の最後の Cadence の報告で見る（[手順書 11-3](../データ収集と学習の手順書.md#11-3-確かめること)）。この道具は、大きく飛んだときしか見つけない。
- **時刻の列がフレームの整数倍だけずれると、本家の読込口は黙って読む。** 0.1 秒（3 フレーム）ずらすと、`LeRobotDataset` はずれた時刻の絵をエラー無しで返した。動画の終わりを越えた所は、絵が止まって見えた。0.05 秒（1.5 フレーム）ずらすと、`FrameTimestampError`（許容 0.0001 秒）で止まった。整数倍のずれは、ファイルの照合（`timestamp` の検査）でしか分からない。

## 何を照らし合わせるか

本家 0.6.2 で、フォロワー（`so101_follower`）とカメラ `front`・`wrist` を記録したときの形（`observation.state` と `action` が 6 関節 `*.pos`、絵 2 つが動画）。検査の名前と中身は道具の先頭の説明が正本。分け方だけ書く。

| 種類 | 何で見るか | 見つけるもの |
|---|---|---|
| ファイル（fail） | `meta/info.json`・`meta/episodes/`・`data/` の parquet を直接読む | 行の数、通し番号の抜け、エピソードの境目と meta の食い違い、`frame_index` の抜け、`timestamp` ≠ `frame_index`/fps、meta の中の動画の長さ、関節の値の範囲 |
| 読込口（fail） | `LeRobotDataset(root=…)`（pyav）で全部の行を読む | 開けない、読めない行、読んだ値と parquet の食い違い |
| 信号（warn） | 読んだ絵（80×60 の灰色）と関節の値（腕の 5 関節。グリッパーは 0〜100 なので「腕が動いている」に入れない） | 腕が動いているのに絵が変わらない（カメラの止まり）、指令が動いているのに 6 関節とも同じ値（読み取りの止まり）、状態・指令・絵が同時に跳ぶ（ループでフレームが抜けた）、指令より状態が先に動く（列のずれ）、遅れが他のエピソードとずれる・カメラの遅れが大きい |

### 遅れの見方

関節の動きと画像の変化を互いにずらしてみて、いちばん相関の高いずらし量を遅れとする。**相関が 0.5 未満なら判定しない。**

初めは、なめらかな正弦波で動き続ける模擬を作った。すると、ずれの無い記録でも遅れを 7〜9 フレームと誤って出した。止まる→動くの区切りが無いと、どのずらし量でも形が似てしまい、遅れが一つに決まらない。そこで模擬を、テレオペに近い「止まる（0.2〜0.5 秒）→ なめらかに動く（0.5〜1.0 秒）」に替えた。フレームの飛びの判定も、初めはエピソード全体の中央値と比べていて、普通の速い動きで誤って出た（ずれの無い記録で 25 件）。いまは前後 3 フレームと比べる。

## 模擬に入れたずれ

どれもエピソード 1 に入れる（境目のずれだけはエピソード 0 と 1 にまたがる）。局所のずれは、指令がいちばん動いている区間に置く（いちばん見つけやすい所）。右の列は、種 3 つで出た警告を全部書いた。

| 名前 | 入れたこと | 出た検査（種 1〜3） |
|---|---|---|
| `cam_lag_front` | 正面の絵が 6 フレーム（200 ms）遅れる | camera_lag_large、lag_inconsistent |
| `stale_front` | 正面の絵が 18 フレーム止まる（カメラが同じ絵を返す） | stale_camera |
| `state_hold` | 6 関節の読みが 13 フレーム同じ値（絵は動いている） | state_hold |
| `frame_skip` | ループが 10 フレーム落とす（全部の列が一度に飛ぶ） | time_jump |
| `action_shift` | 指令の列が 6 フレーム遅れて入る（状態が指令より 4 フレーム先に動く） | action_after_state、lag_inconsistent |
| `drop_rows` | 書いた後で 5 行消す（meta は直さない） | rows_total、index、episode_boundary、frame_index、decode（meta の行数が parquet より多く、終わりの 5 行が読めない。動画の欠けを見つけたのではない）。time_jump は出なかった |
| `bad_timestamp` | 書いた後で時刻を 0.1 秒（3 フレーム）ずらす | timestamp。ほかに stale_camera（種 1〜3）、lag_inconsistent（種 2・3） |
| `episode_boundary` | 書いた後で、エピソード 0 の最後の 3 行を 1 に入れる | episode_boundary（0 と 1）、frame_index、time_jump（種 1〜3）、lag_inconsistent（種 3） |

## 言えないこと

- **実物の記録での誤った警告の数。** 模擬は次の点で実物より易しい。
  - 絵は、止まった背景の上で腕だけが動く。光の揺れ、影、人の手が無い。
  - 2 つのカメラの絵は、関節の値と同じ行から描くので、カメラの遅れは作り方から 0 になる（入れた回は 6）。
  - 指令には雑音が無い。状態は指令を 2 フレーム遅らせ、0.05° の雑音を足しただけ。
  - 状態に毎フレーム雑音があるので、模擬では「6 関節とも同じ値」が誤って出ることがない。実物の STS3215 の読みは約 0.088° 刻みで、止まっていると同じ値が続く。指令が小さくゆっくり動くときに誤って出るかは試していない。
  - 動くときは毎回 6 関節が一度に動く。グリッパーだけ、手首の回転だけの動きは無い。
- **ループの飛びを見つける力。** 試したのは、いちばん速い所で 10 フレーム落とした回だけ。本家の記録はフレームを落とさず、遅れたフレームも遅れたまま書く（`lerobot_record.py` の `timer.wait()`）。1〜3 フレームの遅れや、全体がゆっくり遅い記録は、この道具では見えない。Cadence の報告で見る。
- **動画そのものの欠け。** どの回も mp4 には手を付けていない。`video_span` は meta の中の数どうしを比べるだけで、動画のフレーム数は数えていない。動画が途中で切れていても、絵が止まって読めるだけかもしれない（上の 0.1 秒の回）。
- **カメラが長く止まった記録。** 止まりの判定は、エピソードの中の画像の変化の中央値と比べる。エピソードの大半で止まると中央値が下がり、見逃す。遅れの判定も相関が 0.5 を割って飛ばす。
- **`lerobot-record` が書いた記録との違い。** 模擬は `LeRobotDataset.create`・`add_frame`・`save_episode`・`finalize` で書いた。本家の記録とは次が違う。
  - features は、記録のコマンドではロボットの features から組む（`lerobot_record.py` 418〜431 行）。模擬は 6 関節の名前を手で並べて `hw_to_dataset_features` に渡した。形は同じはずだが、比べてはいない。
  - 記録のコマンドは、絵を書くスレッドの数・動画の書き方・`streaming_encoding` を `create` に渡す（469〜484 行）。模擬は既定のまま。
  - 実物のエピソードは 20 秒（600 フレーム）、模擬は 4 秒（120 フレーム）。
- **再生。** 段の名前は「記録・再生」だが、記録を腕で流し直すことは試していない。
- 模擬 1 つを作るのに 3〜4 分かかる（640×480 の絵を PNG に書いて AV1 にする）。照合は 1 つ 40 秒ほど（読むのに 21〜25 秒）。

## このパソコンで見たこと

- `torchcodec` は入っているが読めない（`libtorchcodec_core4.dll`）。本家は `pyav` に切り替える（`lerobot/utils/import_utils.py` の `get_safe_default_video_backend`）。道具は初めから `pyav` を使う。
- 本体 0.6.2 では、フォロワーの関節の単位の既定が度（`use_degrees: True`）、グリッパーは 0〜100。
