## 項目

### K-0041 最新のモデルは指示を文字どおりに受け取る。「変更を提案して」と頼むと提案で終わるので、直してほしいなら「この関数を直して」と動詞で頼む。

対象: 現行の全モデル ／ 根拠: 公式 ／ 確認日: 2026-11-16 ／ 見直し期限: 2027-05-16

**要点**
- 積極的に動くか慎重に動くかの既定は、システムプロンプトで切り替えられる。

出どころ: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices

### K-0077 AI が書いたコードは、動いても SQL インジェクション・XSS などの脆弱性を含むことが多いので、書かせて終わりにせず、観点を名前で挙げたセキュリティのレビューを別の段として入れ、道具（解析・テスト）の結果を返して直させる。

対象: LLM のコード生成全般（Claude 3.5 Sonnet・Claude 4 Sonnet を含む測定あり。Claude 5 系での測定は見つけていない） ／ 根拠: 論文 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-05-17

**要点**
- 動くかどうかと、安全かどうかは別。テストが通っても脆弱なことがある。
  - SusVibes（ICML 2026、実在の OSS の機能追加 186 件、エージェントで）: SWE-Agent＋Claude 4 Sonnet は約 57% が正しく動いたが、安全だったのは 11.8%。
  - BaxBench（2025、バックエンド 392 題を実際の攻撃で確かめる）: いちばん良い o1 でも正しいのは 62%、正しいもののおよそ半分が攻撃できた。Claude 3.5 Sonnet は正しい 53.6%、正しくて安全 32.9%。
  - Veracode（2025、100 超のモデル・80 題。企業の発表で、報告の本文は読んでいない）: 45% に OWASP Top 10 の脆弱性。XSS は 86% で失敗。構文の正しさは上がっても、安全さは上がっておらず、大きいモデルが目立って良いわけでもない。
  - 古いモデルでも同じ傾向（Copilot 2021 で約 40%、Pearce ら IEEE S&P 2022）。
- **探させると見つかることがある。** 書くときに避けられなかった欠陥を、レビューを頼むと見つけることがある（ChatGPT は自分の脆弱な Java の 90.6%、Python の 63.6% を指摘）。ただし言語で大きく違い、C ではほとんど見つけられなかった（ChatGPT 7%、Bard 0%）。自分の書いたものより相手のモデルの書いたものの方がよく見つけた、という要約もあるが、それは主に C の話で、Java・Python では逆だった（Ambati ら）。Gong ら（2024、GPT-3.5・GPT-4）は、自分が書いたコードの修理が苦手なこと（死角）を報告し、意味解析の道具の結果を返しながら直させると、直せる割合が 33〜60% から 66〜86% に上がった。**一回頼めば十分ではなく、道具の結果を返す繰り返しが効く**、が今ある証拠に近い。
- 公式（Claude Code の security のページ）も、提案されたコードとコマンドの安全を確かめるのは使う人の責任だとしている。
**注意**
- 数字はベンチマークの値で、題の作り方で大きく変わる。Claude 5 系で測った研究は見つけていない（2026-11-17）。「Claude 5 系なら大丈夫」とも「同じだけ弱い」とも言えない。
- 別の段のレビューでも全部は拾えない。公式も Code Review は見逃すことがある、security-guidance は多層の守りの1枚と書いている。人の確認を残す。
- 見直しの段の効き目の測定は、主に GPT-3〜4・ChatGPT・Bard の世代。「書いたのと別の文脈で見る」がどれだけ効くかは、証拠が割れている（上の Ambati ら）。別の文脈にするのは、書いた会話の思い込みを持ち込まないための勧め（K-0024 の別の文脈のレビュー）で、セキュリティについては Claude で確かめていない（USAGE_LOG で試す候補）。

出どころ: https://arxiv.org/abs/2512.03262、https://arxiv.org/abs/2502.11844、https://arxiv.org/abs/2108.09293、https://www.veracode.com/press-release/ai-generated-code-poses-major-security-risks-in-nearly-half-of-all-development-tasks-veracode-research-reveals/、https://arxiv.org/abs/2408.10495、https://cyberlab.usask.ca/papers/LLM_vulnerability_analysis__IEEE_CSR.pdf、https://code.claude.com/docs/en/security

### K-0078 「安全なコードを書いて」の一言やセキュリティ専門家の役（ペルソナ）を足すだけでは、生成されるコードの脆弱性はあまり減らない。具体的な観点でのレビューと直しの段を別に設ける方が効く。

対象: LLM のコード生成全般（一言の注意が効かないことは Claude 3.5 Sonnet・Claude 4 Sonnet でも測定あり。見直しの段の効き目は GPT-3〜4 での測定） ／ 根拠: 論文 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-05-17

**要点**
- 依頼に脆弱性の注意を足しても、エージェントの実務に近い題では安全さはわずかしか上がらず、正しく動く割合は下がった（SusVibes、ICML 2026。この試しは SWE-Agent＋Claude 4 Sonnet だけで、安全 11.8%→14.5〜15.1%、正しい 57%→50.0〜55.4%）。
- 一般的な「安全に」の注意は、考える（reasoning）モデルではかなり効いたが、そうでないモデルでははっきりしなかった。Claude 3.5 Sonnet は安全 32.9%→34.5% で、正しく動く割合は 53.6%→45.5% に下がった（BaxBench 2025）。
- 古いモデルでの比較（Tony ら、ACM TOSEM 2025、GPT-3・3.5・4）: 「批評してから直す」（RCI）で弱点が GPT-4 で 109→38 に減った。「secure」と足すだけは 109→98、セキュリティの役（ペルソナ）はどのモデルでもいちばん効かなかった。
**注意**
- 「批評してから直す」の数字は古いモデル。Claude 5 系での測定は見つけていない（2026-11-17）。
- 考えるモデルでは一言の注意も効いたという結果があるので、「全く効かない」とは書かない。

出どころ: https://arxiv.org/abs/2512.03262、https://arxiv.org/abs/2502.11844、https://arxiv.org/html/2407.07064v2

### K-0079 Claude Code にはセキュリティを見る道具が段ごとにある。編集ごと・ターンごと・コミットごとに見る security-guidance プラグイン、ブランチの差分を見る /security-review、深く調べる /claude-security、PR を見る Code Review（管理された）と GitHub Action claude-code-security-review。/code-review（/review）は既定では正しさを見るもので、セキュリティ専用ではない。

対象: Claude Code ／ 根拠: 公式 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-02-17

**要点**
| 道具 | いつ・何を見る | 使える人 | 観点を足す方法 |
|---|---|---|---|
| security-guidance プラグイン（`/plugin install security-guidance@claude-plugins-official`） | 編集ごとに型で、ターンごとに差分をモデルで、Claude が Bash で行うコミット・プッシュでより深く（自分のシェルで打ったコミットは見ない）。注入、安全でないデシリアライズ、危ない DOM API を拾う | 全プラン | `.claude/claude-security-guidance.md`、`.claude/security-patterns.yaml` |
| `/security-review` | 今のブランチの変更（origin の既定のブランチとの差分）。注入・認証の問題・データの露出 | 全員。`origin` のリモートが要る | 公式のページでは見つけていない（Action の README には `.claude/commands/` に写して直せるとある） |
| `/claude-security`（Claude Security プラグイン） | 複数のエージェントで深く調べる。直しは自動では当てない。走らせるたびに結果が変わりうる | 有料プラン、Anthropic API、ほかの提供元。Pro は `/config` で Dynamic workflows を入れる | — |
| Code Review（管理された PR のレビュー） | PR の論理の誤り・脆弱性・境界の抜け。既定は正しさが中心 | Team・Enterprise | `REVIEW.md` と `CLAUDE.md` |
| GitHub Action `anthropics/claude-code-security-review` | PR の変更したファイルを見て、行にコメント。DoS・レート制限などの誤検知を除く仕組みがある | API キー | `custom-security-scan-instructions`、`false-positive-filtering-instructions`（どちらも文のファイル） |
| `/code-review`（別名 `/review`） | 今の差分の正しさのバグ。セキュリティ専用ではない | 全員 | 主に CLAUDE.md。`code-review` という名前のスキルを作ると `/code-review` は置き換わるが、`/review` は付属のレビューのまま |
**注意**
- GitHub Action の README: プロンプトインジェクションへの対策はしておらず、信頼できる PR だけに使う。外からの PR には承認を求める設定を勧めている。README の既定のモデルは claude-opus-4-1 で古い可能性がある（`claude-model` で変えられる）。
- 公式は Code Review について「見逃すことがある」、security-guidance について「多層の守りの1枚で、全部の解決ではない」と書いている。ほかの道具も、全部拾えると考えない。
- 自分のプロジェクトの観点は、security-guidance なら `.claude/claude-security-guidance.md` に書ける。
- Anthropic の発表（2026-02-20、Claude Code Security の研究プレビュー）でも、直しは人の承認なしには当てないとしている。

出どころ: https://code.claude.com/docs/en/commands、https://code.claude.com/docs/en/security、https://code.claude.com/docs/en/security-guidance、https://code.claude.com/docs/en/claude-security、https://code.claude.com/docs/en/code-review、https://code.claude.com/docs/en/code-review-customize、https://code.claude.com/docs/en/code-review-local、https://github.com/anthropics/claude-code-security-review、https://www.anthropic.com/news/claude-code-security

### K-0024 AI に「通った・落ちた」が分かる確かめ方（テスト・ビルド・Stop フック）を渡し、終わったら証拠（実行したコマンドと出力）を出させる。

対象: Claude Code ／ 根拠: 自分で確認 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-05-17

**要点**
- /verify で動かして確かめ、/code-review で別の文脈のレビュー、/goal で完了条件を満たすまで続けさせる。
- 「全部のテストが通りました」という自己申告だけを信じない。
**自分の記録（調べたプロジェクト（記録は Claude_knowhow の docs/knowledge、2026-11-17 の考察）、2026-11-17 に調べた）**
- 「できた」と言ってから人が見て違っていた、が約 30 件で、損失がいちばん大きい失敗だった（点検の赤の原因が自分の消した計算結果、記録を書いた直後に「まだぐちゃってなってる」、出した数字が違っていた）。
- 記録を書いたことは、直した証拠ではない。
- 人や実機の手を使わせる前に、シミュレータと机上の点検を通さないと、信頼が一気に落ちた（10 月末の実機の段階に約 6 件）。
- 裏付けたのは「確かめずに『できた』と言うと人が検証役になる」という向き。/verify・/goal などの道具の効き目は確かめていない。

出どころ: https://code.claude.com/docs/en/best-practices
