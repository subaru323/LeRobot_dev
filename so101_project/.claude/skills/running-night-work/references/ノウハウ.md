### K-0024 AI に「通った・落ちた」が分かる確かめ方（テスト・ビルド・Stop フック）を渡し、終わったら証拠（実行したコマンドと出力）を出させる。

対象: Claude Code ／ 根拠: 自分で確認 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-05-17

**要点**
- /verify で動かして確かめ、/code-review で別の文脈のレビュー、/goal で完了条件を満たすまで続けさせる。
- 「全部のテストが通りました」という自己申告だけを信じない。
**自分の記録（調べたプロジェクト（記録は Claude_knowhow の docs/knowledge、2026-11-17 の考察）、2026-11-17 に調べた）**
- 「できた」と言ってから人が見て違っていた、が約 30 件で、損失がいちばん大きい失敗だった（点検の赤の原因が自分の消した計算結果、記録を書いた直後に「まだぐちゃってなってる」、出した数字が違っていた）。
- 記録を書いたことは、直した証拠ではない。
- 人や実機の手を使わせる前に、シミュレータと机上の点検を通さないと、信頼が一気に落ちた（10 月末の実機の段階に約 6 件）。
- 裏付けたのは「確かめずに『できた』と言うと人が検証役になる」という向き。/verify・/goal などの道具の効き目は確かめていない。

出どころ: https://code.claude.com/docs/en/best-practices

### K-0029 仕組み（ハーネス）の部品は「モデルが1人ではできないこと」への手当てで、モデルが良くなると要らなくなる。新しいモデルが出たら、外せる部品と指示を見直す。

対象: 長時間のアプリ開発の仕組み（2026-03〜04 の記事） ／ 根拠: 公式 ／ 確認日: 2026-11-16 ／ 見直し期限: 2027-05-16

**要点**
- 例: Sonnet 4.5 の「文脈が残り少ないと早く切り上げる」対策だった文脈のリセットは、Opus 4.5 で要らなくなった。作業を短く区切る仕組みも Opus 4.6 で外した。
- Anthropic は Opus 5・Fable 5 向けに Claude Code のシステムプロンプトを8割以上削り、コーディングの評価で測れる悪化は無かったと書いている（2026-07-24）。「決まりを与える」から「判断を任せる」へ。
- 仕様を書く役には、細かい技術ではなく、製品の文脈と大まかな設計だけを書かせる（仕様の誤りが実装に広がるため）。
**注意**
このノウハウ集の管理（README の6節の4）の根拠の1つ。

出どころ: https://www.anthropic.com/engineering/harness-design-long-running-apps、https://www.anthropic.com/engineering/managed-agents、https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/

### K-0080 Claude デスクトップの予約タスク（ローカル）は、アプリが開いていて PC が起きているときだけ走り、前の回やほかの予約タスクが動いていればその回は飛ばされ、逃した回はアプリを開いた・PC が起きたときに直近の1回だけ取り戻して走る（昼に走ることもある）。

対象: Claude Code デスクトップ 1.1.5368 以降 ／ 根拠: 公式 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-02-17

**要点**
- 公式: 「Tasks only run while the desktop app is running and your computer is awake.」スリープ中の回は飛ばされる。設定の Keep computer awake でアイドルのスリープを防げる（蓋を閉じると寝る）。
- 飛ばされる理由（履歴の skipped にマウスを載せると出る）: PC が寝ていた、前の回がまだ動いていた、ほかの予約タスクが既に動いていた。
- 逃した回: 過去7日分を見て、いちばん最近の1回だけ取り戻して走らせる。公式は、時刻が大事なら指示文に「〇時を過ぎていたら〜」のような守りを書くよう勧めている。
- 各タスクは、予定の時刻から数分遅れて始まる（同じタスクはいつも同じずれ）。
- アプリを開いたときに始まる取り戻しの回は、モデルが「Default · Set by admin」なら、アカウントの既定のモデルで走ることがある。
- 設定で Worktree を選ぶと、回ごとに別の worktree で走る（フォルダの中の作業の列を回どうしで受け渡すなら選ばない）。
- 権限: タスクごとに権限のモードを決める。作った後に Run now して、出た確認に「always allow」を選んでおくと、次から止まりにくい（詳細ページで取り消せる）。フォルダの中の編集なら、モードを Accept edits にする。毎回確認を求める MCP の道具（requiresUserInteraction）を使う回は毎回止まる。
- 指示文は `~/.claude/scheduled-tasks/<名前>/SKILL.md`。予定・フォルダ・有効かどうかはそこに無い。
- PC を切っていても走らせたいなら、クラウドの予約タスク（ルーティン）。こちらは手元のファイルを見られない（新しい clone）。
**注意**
- 夜に複数のプロジェクトの予約タスクを並べると、互いに飛ばし合う。時刻をずらし、1回を短くする。
- Claude_knowhow の 2026-11-17 の夜、1回目（0:22 ごろ）の跡が無かった。理由は履歴の skipped で確かめられる（このとき別のプロジェクトの 23:30 の予約タスクが動いていた可能性がある。確かめていない）。

出どころ: https://code.claude.com/docs/en/desktop-scheduled-tasks

### K-0083 見つけるだけの監査は、直す担当と期限が無いと赤が慢性になり、新しい赤が埋もれる。慢性の赤は直すか「受け入れ済み」に降ろす。

対象: AI に点検を回させるプロジェクト（夜の点検など） ／ 根拠: 自分で確認 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-05-17

**要点**
- 調べたプロジェクト（記録は Claude_knowhow の docs/knowledge、2026-11-17 の考察）の夜の点検（10-30〜11-17）: 返事の無い依頼が 0→18→22 件（3日で増え、そのまま）、門は 18 日赤のまま、仮の値の NG は 661→1293 件。朝の報告は「昨夜から増えた赤」だけを見る形に変わった。
- 落とし穴の文書にも「ほかの NG に埋もれて読んでいなかった」がある。
**注意**
- 1つのプロジェクトの観察。

出どころ: Claude_knowhow の検証の記録

### K-0084 並行して動く AI のセッションには、共有の文書に同時に追記させず、セッションごとの追記だけのログを持たせる。返事の無い依頼は検出し、止まったセッションへの依頼は期限で取り下げる。

対象: 複数のセッションを並行で動かす Claude Code のプロジェクト ／ 根拠: 自分で確認 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-02-17

**要点**
- 調べたプロジェクト（記録は Claude_knowhow の docs/knowledge、2026-11-17 の考察）: 「1つの md に3台が追記すると必ず壊れる」（進行ログの道具の冒頭。台＝並行のセッション）。セッションごとの jsonl に1行ずつ追記し、時刻順に混ぜて読む形にした。古い前提での作業や二重作業の訂正（約 30 件）は、この後減った。
- 返事の無い依頼は検出の道具が数えたが、片付ける決まりが無く、3日で 0→22 件に増えてそのまま残った。止まったセッションへの依頼が 80〜137 時間残った。
- 番号（失敗の記録の F-nn など）の取り合いは、使う前にログに「決めた」を出して避けた。
**注意**
- 1つのプロジェクトの観察。

出どころ: Claude_knowhow の検証の記録
