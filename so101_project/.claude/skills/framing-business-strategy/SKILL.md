# 事業戦略の視点で組み立てる（種のパッケージ 2026-11-26.1347）

> この種は試作（実務でまだ確かめていない）。

このパッケージのほかの種: `ai-knowhow`（Claude と Claude Code の使い方全般（モデル・effort・機能・指示の書き方）と、既存のプロジェクトの昔の定石の見直し）、`enforcing-project-rules`（プロジェクトの決まりを、文章でなく仕組み（打つ前のフック・始めの点検・決まりと判定の表・担当つきの監査）で守らせる）、`reviewing-security`（コードの変更を SQL インジェクション・XSS などの観点で見直し、攻撃の筋道つきで指摘して直す）、`running-night-work`（人がいない間（夜など）に AI に作業を進めさせる仕組み（作業の列・予約タスク・朝の報告）を組む）、`writing-project-docs`（CLAUDE.md・STATUS.md・AI への依頼書・スキルを、ノウハウに沿って書く・見直す）。その場面ならそちらを使う。

技術者の普段の問いは「この機能を、今の案件で、作れるか」。事業を考える人は同じ話を、3つの軸の右側から見る。この種は、その右側から考える型を順に当て、提案を1枚にする。型の中身と用語は [references/型.md](references/型.md)、1枚の形は [references/一枚の型.md](references/一枚の型.md)。

| 軸 | 左（普段） | 右（事業の目） |
|---|---|---|
| 時間 | 今の案件 | 3〜5年後の当たり前 |
| 高さ | この機能 | 業界で誰が儲かるか |
| 守り | 作れるか | 真似されないか |

## 使い分け

- **組み立てる**: 「次にどこへ広げるか」「この企画をどう出すか」と頼まれたら、下の手順 1〜7 を順に当てる。
- **書き戻す**: 人の提案・計画・資料を渡されたら、まず「この提案はどの問いへの答えか」を1文で言う。次に手順 1〜6 の6つに分けて書き出し、空いた所と弱い所を挙げ、足りない所は「次に聞くこと」にする。見るのは提案の形で、提案した人は評価しない（目的は型の練習と次に聞くことの洗い出しで、人の良し悪しを付けると利用者が使いにくくなるため）。

## 手順

1. **問いを1文にする（イシュー）。** 「答えが出たらやることが大きく変わるか」と「今の手持ちで答えが出せるか」の両方を満たす形に絞る。主語と、何と比べるかを入れる。例: 「AI で何ができるか」→「AI 検査が当たり前になったとき、うちの価値はどこに残るか」。頼みが広すぎるときは、絞った問いを示して利用者に確かめてから進める（問いを外すと後の作業が全部無駄になるため）。
2. **答えを先に仮に置く（仮説）。** 今ある材料で「たぶんこう」を1文で置き、理由を3つ、各理由に根拠を付ける（ピラミッドの形）。各理由に「これが本当なら何が見えるはずか」を1行添え、確かめる材料をそれだけに絞る（仮説が無いと、集める材料に終わりが無いため）。外れたら直す前提で書く。
3. **大きさを式で出す（フェルミ推定）。** 知らない数を、だいたい分かる数の掛け算の木に分ける。各数に出どころ（統計や資料の名前）か「仮」を書く。計算はコードで行い（掛け算の桁の誤りを防ぐため。この種の決め）、強気・ふつう・弱気の3通りを表にし、どの数が結果を一番動かすかを1行で言う。目的は桁を外さないこと。数字だけでなく式と前提を出す（後から誰でも検証できるように）。出どころは、検索や手元の資料で確かめられるときだけ書く。確かめられない数は「仮」にし、一番効く数から順に「次に確かめること」へ回す（思い出した統計は古いか誤っていることがあるため）。
4. **真似されない理由を型で言う（堀）。** 規模・つながり・反競合（強い会社が真似すると自分の今の事業を傷つける形）・乗り換えの手間・ブランドと信頼・独自の資源・作り込み・先行の蓄積のどれか（型.md）。「技術が優れている」「精度が高い」は堀に数えない（相手が人とお金を入れれば数か月で埋まるため）。技術の差しか無いなら、それを堀の型に変える順（例: 先に入って記録を溜める）を書く。打ち手どうしのつながり（ストーリー）も挙げる。
5. **技術が当たり前になった後に残る物を書く（コモディティ化）。** その技術がどこでも買える日を先に置き、価値が移る「周り」（つなぐ場所・たまるデータ・任せられる信頼）のうち、今から押さえる物を挙げる。強い会社が手を出しにくい入り口（イノベーションのジレンマ）があれば書く。
6. **顧客の用事と決め方を書く。** 顧客が片付けたい用事（ジョブ）を製品名でなく用事で書き（用事で書くと、人を雇う・外注するなどの代わりの手も競争相手として見えるため）、それらも競争相手に数える。使う人・決める人・払う人・止められる人を分け、それぞれの合格条件を書く。新しい技術なら、今の客がどの段か（新しもの好き・先を見る人／慎重な多数派／保守派）と、谷（キャズム）を越えたか（同業の実績があるか）を分けて書き、越える最初の1業界を書く。
7. **分かれる所は決め手で言う。** 詳しい人どうしでも分かれる論点は、どちらが正しいかでなく決め手で書く。
   - 客の声を待つか、先回りするか: 市場が桁違いに大きく、小さく試せて外れても失う量が小さいなら先回り。人とお金が少なければ客の声を待つのが基本。決め手の桁は手順3で出す。
   - 狭く深くか、広く汎用か: 定番は順番で両立させる形。1業界で谷を越えて実績を作り、その実績を持って隣の業界へ。汎用の土台は、つなぐ部品を作り溜めて後から広げる。
   - 材料が足りなくても、質問を返すだけで終えず、決め手を測る行動を1つ出す。誰に何人聞くか、期間と人の割き方、何が出なければやめるかを数で書く（例: 作る前に見込みの客 20 人に聞き、3か月で「払う」と言う会社が3社出なければやめる）。足りない情報の質問はその後に添える（2026-11-26 の比べで、質問だけで終えた答えが、行動まで出した答えに負けたため）。

## 仕上げ

- 1枚の形（一枚の型.md）に入れ、各行に確からしさの札（【確】出どころあり・【一般】定番の型・【推】自分の推測・【仮】置いた数）を付ける（読む人が、どこを確かめればよいか分かるように）。最後に「次に確かめること」を3つまで。
- 終える前に、一枚の型.md の点検の問いで6つが埋まっているかを確かめる（K-0046）。
- 方向を大きく変える判断や、利用者が人に出す提案なら、推論を見ていない別のエージェントに、1枚と一枚の型.md の点検の問いだけを渡して独立に見直させる案を出す（議論させるより独立した見直しが効く、K-0028）。費用がかかるので、走らせるのは利用者が承認してから。
- 業界の構造・顧客の事情は、AI の記憶より、顧客の中期経営計画・決算説明資料・業界の統計を先に見る（記憶は古く、業界ごとに違うため。この種の決め）。手元に無ければ、利用者に資料を頼むか「次に確かめること」に回す。

## 限界

- 型は定番の経営書から取った一般の型で、この種の効き目はまだ測っていない。
- 例の数字はすべて考え方を見せるための仮の値。
- 投資や財務の助言はしない。
- この種は試作。作業の返事には、マスターの記録の話を書かない（植えた先の利用者には関係の無い頼みに見えるため。2026-11-26 の比べで、返事30回のうち8回に出ていた）。利用者が種の効き目を聞いたとき、または種を試していると言ったときだけ、マスターの記録（マスター（Claude_knowhow）の results/USAGE_LOG.md。マスターの場所は SEED.json の master）に1行書く案を出す。
