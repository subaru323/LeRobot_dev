### K-0024 AI に「通った・落ちた」が分かる確かめ方（テスト・ビルド・Stop フック）を渡し、終わったら証拠（実行したコマンドと出力）を出させる。

対象: Claude Code ／ 根拠: 自分で確認 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-05-17

**要点**
- /verify で動かして確かめ、/code-review で別の文脈のレビュー、/goal で完了条件を満たすまで続けさせる。
- 「全部のテストが通りました」という自己申告だけを信じない。
**自分の記録（調べたプロジェクト（記録は Claude_knowhow の docs/knowledge、2026-11-17 の考察）、2026-11-17 に調べた）**

- 記録を書いたことは、直した証拠ではない。
- 人や実機の手を使わせる前に、シミュレータと机上の点検を通さないと、信頼が一気に落ちた（10 月末の実機の段階に約 6 件）。

### K-0028 AI 同士に議論させると答えが良くなる、とは確かめられていない。効くとされるのは、推論を見ていない別のエージェントによる独立したレビュー。

対象: Opus 5・Sonnet 5 など（研究記事）、Claude Code ／ 根拠: 公式 ／ 確認日: 2026-11-16 ／ 見直し期限: 2027-05-16

**要点**
- 合議は、みんなが既に知っている情報にまとまり、一部の者だけが知る事実が出てこない。
- 文脈・仕組み・モデルが同じエージェントはほとんど同じ行動をとるので、1体の悪い判断を多くが同じように下し、全体の失敗になる（相関であって、うつるのではない）。
- 利用者ごとに別のエージェントを付けたチームは、1体の調整役より成績が悪く、作り話も多かった（作り話は Opus 5 で 58%、Sonnet 5 で 53%、1体だと 17〜20%）。
- **ただし、2本の研究は議論そのものは試していない**（試したのはエージェントどうしのやり取り）。逆に、互いにレビューし別の判定役が決める調整された群れが、独立に動いたものより多くの脆弱性を見つけた例もある（266件 対 21件、Mythos Preview）。
- 独立したレビューの部分の出どころは best-practices。
- このフォルダの結果とも合う: EXP-002 で「複数の立場で計画を見る」の差は小さかった。先行研究（Huang 2023）でも、議論は同じ数の答えの多数決に勝たなかった。
**注意**
動画の言説 U-09（量産して反論役に潰させる）とぶつかる。

出どころ: https://www.anthropic.com/research/multiagent-systems、https://alignment.anthropic.com/2026/worse-together/、https://code.claude.com/docs/en/best-practices

### K-0072 claude plugin eval は、各ケースをプラグイン有りと無しで既定で3回ずつ（1ケース6回）走らせて差を測る。毎回が本物のモデル呼び出しで費用がかかり、CLAUDE.md や .claude/ や自分の設定は読まれない。

対象: Claude Code 2.1.269 以降 ／ 根拠: 公式 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-05-17

**要点**
- 公式: 「Each case runs three times with your plugin and three times without it, so one case is six runs.」「Every eval run and every judge grader is a real model call on your account.」
- 置き場は `evals/` に1ケース1フォルダ、`prompt.md` と `graders/*.md`。採点は regex・tool_used・tool_order・file_exists・llm・baseline。合格の線 `--threshold` の既定は 1.0。
- `claude plugin eval init` で叩き台、`claude plugin eval .` で実行。`claude plugin validate` は形だけを見て、振る舞いは見ない。
- 分離: 「Nothing personal or project-level loads.」ケースに要るスキル・フック・MCP はプラグインに入れておく。
- Bash・Write・Edit は既定で使えず、`--allow-tools` で許す。Windows にはサンドボックスが無いので、Bash（や PowerShell）を許すなら WSL2 で走らせる。CI では `--trust-plugin --json` と、モデル（評価される側と採点する側の両方）の固定。
**注意**
- 費用の見積もりは「ケース数 × 6 回 + 採点」。採点は llm・baseline の採点1つにつき、1回の実行ごとに短い呼び出し3回。

出どころ: https://code.claude.com/docs/en/plugin-evals

### K-0077 AI が書いたコードは、動いても SQL インジェクション・XSS などの脆弱性を含むことが多いので、書かせて終わりにせず、観点を名前で挙げたセキュリティのレビューを別の段として入れ、道具（解析・テスト）の結果を返して直させる。

対象: LLM のコード生成全般（Claude 3.5 Sonnet・Claude 4 Sonnet を含む測定あり。Claude 5 系での測定は見つけていない） ／ 根拠: 論文 ／ 確認日: 2026-11-17 ／ 見直し期限: 2027-05-17

**要点**
- 動くかどうかと、安全かどうかは別。テストが通っても脆弱なことがある。
  - SusVibes（ICML 2026、実在の OSS の機能追加 186 件、エージェントで）: SWE-Agent＋Claude 4 Sonnet は約 57% が正しく動いたが、安全だったのは 11.8%。
  - BaxBench（2025、バックエンド 392 題を実際の攻撃で確かめる）: いちばん良い o1 でも正しいのは 62%、正しいもののおよそ半分が攻撃できた。Claude 3.5 Sonnet は正しい 53.6%、正しくて安全 32.9%。
  - Veracode（2025、100 超のモデル・80 題。企業の発表で、報告の本文は読んでいない）: 45% に OWASP Top 10 の脆弱性。XSS は 86% で失敗。構文の正しさは上がっても、安全さは上がっておらず、大きいモデルが目立って良いわけでもない。
  - 古いモデルでも同じ傾向（Copilot 2021 で約 40%、Pearce ら IEEE S&P 2022）。
- **探させると見つかることがある。** 書くときに避けられなかった欠陥を、レビューを頼むと見つけることがある（ChatGPT は自分の脆弱な Java の 90.6%、Python の 63.6% を指摘）。ただし言語で大きく違い、C ではほとんど見つけられなかった（ChatGPT 7%、Bard 0%）。自分の書いたものより相手のモデルの書いたものの方がよく見つけた、という要約もあるが、それは主に C の話で、Java・Python では逆だった（Ambati ら）。Gong ら（2024、GPT-3.5・GPT-4）は、自分が書いたコードの修理が苦手なこと（死角）を報告し、意味解析の道具の結果を返しながら直させると、直せる割合が 33〜60% から 66〜86% に上がった。**一回頼めば十分ではなく、道具の結果を返す繰り返しが効く**、が今ある証拠に近い。
- 公式（Claude Code の security のページ）も、提案されたコードとコマンドの安全を確かめるのは使う人の責任だとしている。
**注意**
- 数字はベンチマークの値で、題の作り方で大きく変わる。Claude 5 系で測った研究は見つけていない（2026-11-17）。「Claude 5 系なら大丈夫」とも「同じだけ弱い」とも言えない。
- 別の段のレビューでも全部は拾えない。公式も Code Review は見逃すことがある、security-guidance は多層の守りの1枚と書いている。人の確認を残す。
- 見直しの段の効き目の測定は、主に GPT-3〜4・ChatGPT・Bard の世代。「書いたのと別の文脈で見る」がどれだけ効くかは、証拠が割れている（上の Ambati ら）。別の文脈にするのは、書いた会話の思い込みを持ち込まないための勧め（K-0024 の別の文脈のレビュー）で、セキュリティについては Claude で確かめていない（USAGE_LOG で試す候補）。

出どころ: https://arxiv.org/abs/2512.03262、https://arxiv.org/abs/2502.11844、https://arxiv.org/abs/2108.09293、https://www.veracode.com/press-release/ai-generated-code-poses-major-security-risks-in-nearly-half-of-all-development-tasks-veracode-research-reveals/、https://arxiv.org/abs/2408.10495、https://cyberlab.usask.ca/papers/LLM_vulnerability_analysis__IEEE_CSR.pdf、https://code.claude.com/docs/en/security

### K-0083 見つけるだけの監査は、直す担当と期限が無いと赤が慢性になり、新しい赤が埋もれる。慢性の赤は直すか「受け入れ済み」に降ろす。
