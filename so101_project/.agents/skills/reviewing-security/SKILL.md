# コードのセキュリティを見直す（種のパッケージ 2026-11-17.1234）

> この種は試作（実務でまだ確かめていない）。

このパッケージのほかの種: `ai-knowhow`（Codex と Codex の使い方全般（モデル・effort・機能・指示の書き方）と、既存のプロジェクトの昔の定石の見直し）、`enforcing-project-rules`（プロジェクトの決まりを、文章でなく仕組み（打つ前のフック・始めの点検・決まりと判定の表・担当つきの監査）で守らせる）、`running-night-work`（人がいない間（夜など）に AI に作業を進めさせる仕組み（作業の列・予約タスク・朝の報告）を組む）、`writing-project-docs`（CLAUDE.md・STATUS.md・AI への依頼書・スキルを、ノウハウに沿って書く・見直す）。その場面ならそちらを使う。

AI が書いたコードは、動いても脆弱なことが多い（K-0077）。「安全に書いて」の一言ではあまり減らない（考えるモデルでは効いた例もある。K-0078）。だから書く段とは別に、この手順で見る。

## 手順

1. **範囲を決める。** 見るのは変更した所と、その入力がどこから来てどこへ出るか。git があれば `git diff <基のブランチ>...HEAD` と未コミットの差分。無ければ利用者に対象のファイルを確かめる。
2. **別の文脈で見る。** できればサブエージェントに、差分と [references/観点.md](references/観点.md) を渡して見させる。書いた会話の思い込み（「ここは信頼できる入力のはず」）を持ち込まないための勧め。効き目は研究で割れていて、Codex では確かめていない（K-0077）。git に origin があるなら、Codex の `/security-review` を利用者に勧めてもよい（K-0079）。
3. **観点を名前で当てる。** [references/観点.md](references/観点.md) のうち、このコードが触るもの（DB・HTML・シェル・ファイル・認証・外部への通信・秘密情報）の行を全部見る。入力の出どころから危ない使い所（クエリ・HTML・コマンド・パス）まで、値の流れを追う。
4. **道具があれば回す。** プロジェクトに入っている解析の道具（例: semgrep、bandit、eslint のセキュリティの規則、`npm audit`、`pip-audit`）を回し、結果を手順3と突き合わせる。入っていない道具を入れるのは、利用者の承認を取ってから。
5. **報告する。** 下の形で。攻撃の筋道が書けないものは「疑い」に分け、確かなものと混ぜない（誤検知で本物が埋もれないため）。
6. **直して確かめる。** 依頼の範囲で直し、テストを回す。安全にすると動かなくなることがあるので、動きも確かめる（K-0078）。直した所をもう一度手順3で見る。解析の道具の結果は返して直させる（K-0077）。繰り返しは3回まで。残ったものは、誤検知と考える理由をつけて報告に残す。

## 報告の形

| 場所 | 種類 | 攻撃の筋道 | 確かさ | 直し方 |
|---|---|---|---|---|
| `src/db.py:42` | SQL インジェクション（CWE-89） | 検索欄の `q` がそのまま文字列連結でクエリに入る。`' OR 1=1 --` で全件が出る | 確か | パラメータ化したクエリにする |

最後に「見なかった所」（範囲の外、読めなかったファイル、道具が無くて確かめられなかったこと）を書く。

## 限界

- この手順でも全部は拾えない（K-0079: 公式も Code Review は見逃しうると書いている）。認証・お金・個人情報を扱う所は、人のレビューを勧める。
- この種は試作。使ったら、効いたか（拾えたか・誤検知が多かったか）を、利用者の承認を取ってマスターの記録（マスター（Claude_knowhow）の results/USAGE_LOG.md。マスターの場所は SEED.json の master）に1行書くよう提案する。
