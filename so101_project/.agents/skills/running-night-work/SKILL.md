# 人がいない間に AI に作業を進めさせる（種のパッケージ 2026-11-17.1234）

> この種は試作（実務でまだ確かめていない）。

このパッケージのほかの種: `ai-knowhow`（Codex と Codex の使い方全般（モデル・effort・機能・指示の書き方）と、既存のプロジェクトの昔の定石の見直し）、`enforcing-project-rules`（プロジェクトの決まりを、文章でなく仕組み（打つ前のフック・始めの点検・決まりと判定の表・担当つきの監査）で守らせる）、`reviewing-security`（コードの変更を SQL インジェクション・XSS などの観点で見直し、攻撃の筋道つきで指摘して直す）、`writing-project-docs`（CLAUDE.md・STATUS.md・AI への依頼書・スキルを、ノウハウに沿って書く・見直す）。その場面ならそちらを使う。

1回の長い実行より、短い回を数本並べる。途中で切れても、次の回が列のファイルから続きを拾えるため。Claude_knowhow で毎晩動かしている形を元にした。

## 手順

1. **5つの決まりを利用者と決める**（K-0030）。決まらないものがあれば、走らせない。
   - 完了条件: 各作業の「終わり」
   - 自分で確かめる手段: テスト・点検の道具など、通った・落ちたが分かるもの（K-0024）
   - 触ってよい範囲: フォルダ・ファイル。触らないもの、消さない、送らない。git で定期に走らせるなら、ブランチの保護を付ける（K-0030）
   - 止める仕組み: 回数や費用の上限を決める（K-0030）。Claude_knowhow では、1回に作業は1つ、直す・確かめるの繰り返しは3回まで、サブエージェントは3体まで（根拠のある数ではない）
   - 成果の置き場と承認する人: 朝の報告のファイル。方向を変えること・元に戻せない操作（デプロイ、送信、消す）は、決めずに「利用者に聞くこと」へ回す（K-0048: 危ない操作の承認の手順は別に残す）
2. **作業の列のファイルを作る**。[references/列の雛形.md](references/列の雛形.md) を、プロジェクトの `docs/plan/夜の作業.md` などに写して埋める。
3. **予約の実行を作る**。どの道具で予約するかは利用者に聞く。手元のファイルを触るならデスクトップの予約タスク、PC を切っていても走らせたいならクラウドの予約タスク（手元のファイルは見えない）（K-0080）。作るのは利用者が承認してから。
   - 数本を間を空けて並べる（Claude_knowhow では 1.5 時間おきに4本。根拠のある数ではない）。
   - デスクトップの予約タスクは、前の回やほかの予約タスクが動いているとその回が飛ばされる（K-0080）。ほかのプロジェクトの夜の予約と時刻をずらし、1回を短くする。
   - 逃した回は、アプリを開いた・PC が起きたときに1回だけ取り戻して走る。昼に走ることがあるので、指示文に「昼なら何もしない」を入れる（K-0080）。
   - 作業の列のファイルを回どうしで受け渡すので、タスクの設定で Worktree を選ばない（選ぶと回ごとに別の worktree になる。K-0080）。
   - 全部の回を 0 時より後に置くと、朝の報告が1つのファイル（その日の日付）にそろう。
   - 指示文は [references/指示文の雛形.md](references/指示文の雛形.md)。日付を埋め込まない（毎晩使い回すため）。どの回も「表が無ければ作る」ようにしておく（1回目が飛ばされることがある）。
4. **権限を決める**。作った後に Run now し、出た確認のうち許してよいものに「always allow」を選んでおくと、夜に止まりにくい。フォルダの中の編集が主なら、モードを Accept edits にする。毎回確認を求める MCP の道具（requiresUserInteraction）を使う作業は、夜に止まるので入れない（K-0080）。危ない操作は許さないまま残す。全部を許すモード（bypass）にしないのは Claude_knowhow の方針（危ない操作の承認を残すため。K-0048）。
5. **利用者に伝える**。予約の時刻、権限のモード、動く条件（デスクトップならアプリが開いていて PC が起きているとき。Keep computer awake の設定）、朝の報告の場所、飛ばされた回の理由は履歴で見られること（K-0080）。
6. **朝の報告は、新しい赤・慢性の赤・受け入れ済みを分ける。** 慢性の赤には担当と期限を付けるか、理由を書いて受け入れ済みに降ろす。見つけるだけの点検は、赤が慢性になって新しい赤が埋もれる（K-0083）。
7. **朝、報告を読む**のは利用者。止まっていた所（権限の確認待ち、飛ばされた回）を見て、決まりを直す。

並行で動くセッションが複数あるなら、作業の列の1つのファイルに同時に追記させず、セッションごとの追記だけのログにする（K-0084）。

## 注意

- 要約で終わるなど途中で止まる癖が出たら、避けてほしい止まり方を名指しして続けさせる（Fable 5.2 の low/medium、Opus 5.5 の無人実行について。Sonnet 5.5 は名指しは要らず、まず effort を上げる。K-0048）。
- 仕組みの部品はモデルが良くなると要らなくなる。新しいモデルが出たら、外せる決まりを見直す（K-0029）。
- この種は試作。使ったら、効いたかを、利用者の承認を取ってマスターの記録（マスター（Claude_knowhow）の results/USAGE_LOG.md。マスターの場所は SEED.json の master）に1行書くよう提案する。
